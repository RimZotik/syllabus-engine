## Что вы уже знаете

Каждому символу Юникод присваивает номер — кодовую точку (`ord("я")` — 1103). Кодировка — правило, какими байтами записать каждый номер. В UTF-8 кириллица занимает 2 байта, поэтому `len("привет")` — 6, а байтов 12. Теперь эти байты можно увидеть:

```python
print("привет".encode("utf-8").hex(" "))
```

```
d0 bf d1 80 d0 b8 d0 b2 d0 b5 d1 82
```

Видно пары: у каждой буквы первый байт `d0` или `d1`. Осталось понять: почему кодировок так много? Почему «я» с номером 1103 записывается именно байтами `d1 8f`? Почему чтение чужой кодировкой иногда даёт ошибку, а иногда — тихий мусор? <Mark>Текста без кодировки не бывает</Mark>: в файле лежат байты, а символами они становятся только по какой-то кодировке.

</Page>

## Одна таблица на всех — для английского

Чтобы машины разных фирм понимали друг друга, в 1960-е в США приняли общую таблицу символов — <Term id="ascii">ASCII</Term> (American Standard Code for Information Interchange — «американский стандартный код для обмена информацией»): первая версия — 1963 года, привычный вид со строчными буквами — с 1967-го. В ней 128 символов с номерами 0–127, то есть 7 битов: латинские буквы, цифры, знаки препинания и **управляющие символы** — не буквы, а команды вроде «перевести строку» (номер 10, `\n`).

Байт — 8 битов, а ASCII хватает семи. Номера 128–255 остались свободными, и разные страны и фирмы заняли их каждая по-своему: под кириллицу, греческий, иврит. Так появились <Term id="code-page">кодовые страницы</Term> — однобайтовые кодировки: номера 0–127 совпадают с ASCII, а 128–255 отданы своему алфавиту. Для одного только русского языка главных было три: **KOI8-R** (Unix и ранняя электронная почта), **cp866** (старая система DOS 1980-х и до сих пор консоль Windows) и **cp1251** (Windows; в ней до сих пор бывают выгрузки из 1С). Одно и то же слово — разные байты:

```python
for name in ["cp1251", "koi8_r", "cp866"]:
    print(name, "Привет".encode(name).hex(" "))
```

```
cp1251 cf f0 e8 e2 e5 f2
koi8_r f0 d2 c9 d7 c5 d4
cp866 8f e0 a8 a2 a5 e2
```

И наоборот: байт `f0` в cp1251 — «р», в KOI8-R — «П». Если текст записан в одной кодовой странице, а прочитан в другой, его русские буквы превращаются в мусор. А русский и греческий текст в одном файле не записать вовсе: оба алфавита заняли одни и те же номера.

## Одна таблица для всех языков

Выход из «зоопарка» кодовых страниц — одна таблица на всех.

<Theorem kind="definition" title="Юникод"
  formal="Юникод (Unicode) — стандарт, цель которого — перечислить все символы, используемые в человеческих языках, и дать каждому символу уникальный код. Код символа — кодовая точка, целое число от 0 до 0x10FFFF; её записывают как U+ и не меньше четырёх hex-цифр, например U+044F. Способ записи кодовых точек байтами задают кодировки Юникода: UTF-8, UTF-16, UTF-32."
  source="Python docs, «Unicode HOWTO»: Definitions, Encodings (пересказ); The Unicode Standard, гл. 2 «General Structure»">

<Term id="unicode">Юникод</Term> — **набор символов** (character set): общая таблица номеров для всех символов мира. Букве «я» в ней соответствует U+044F (1103), знаку рубля — U+20BD. Какими байтами записать номер, решает кодировка, а кодировок у Юникода несколько.

</Theorem>

Поэтому «файл в кодировке Юникод» — неточная фраза. Программы Windows под ней часто имеют в виду UTF-16, где символ занимает 2 или 4 байта; в файлах и в интернете сегодня почти всегда UTF-8.

## Как устроен UTF-8

Номеров больше миллиона, и писать каждый четырьмя байтами расточительно: английский текст вырос бы вчетверо. UTF-8 тратит столько байтов, сколько нужно номеру, а по первым битам каждого байта видно его роль.

<Theorem kind="rule" title="Схема UTF-8"
  formal="Кодовая точка занимает от 1 до 4 байтов. U+0000…U+007F: 0xxxxxxx. U+0080…U+07FF: 110xxxxx 10xxxxxx. U+0800…U+FFFF: 1110xxxx 10xxxxxx 10xxxxxx. U+10000…U+10FFFF: 11110xxx 10xxxxxx 10xxxxxx 10xxxxxx. Биты номера в двоичной записи заполняют позиции x слева направо, недостающие старшие биты — нули."
  source="RFC 3629 «UTF-8, a transformation format of ISO 10646», раздел 3 (пересказ)">

Первые биты первого байта говорят, сколько байтов у символа: `0` — один, `110` — два, `1110` — три, `11110` — четыре. Каждый следующий байт — **продолжающий** — начинается с `10`. Остальные биты — сам номер.

</Theorem>

Закодируем «я» руками. Номер 1103 больше 127 и меньше 2048 (0x800), значит, нужны 2 байта и 11 битов номера. Во второй байт идут последние 6 битов — это остаток от деления на 2⁶ = 64, в первый — частное:

$$
1103 = 17 \cdot 64 + 15, \qquad 17 = 10001_2, \qquad 15 = 001111_2
$$

Приписываем служебные биты (они выделены):

$$
\mathbf{110}\,10001 \quad \mathbf{10}\,001111 \;=\; \mathrm{D1}\;\mathrm{8F}
$$

Именно `d1 8f` и выдаёт `"я".encode("utf-8")`. Вот сколько байтов занимают латинская буква, «я», знак рубля и скрипичный ключ из нотной записи (U+1D11E):

```python
for ch in ["A", "я", "₽", "\U0001D11E"]:
    print(hex(ord(ch)), len(ch.encode("utf-8")), ch.encode("utf-8").hex(" "))
```

```
0x41 1 41
0x44f 2 d1 8f
0x20bd 3 e2 82 bd
0x1d11e 4 f0 9d 84 9e
```

Латиница — 1 байт, и байты те же, что в ASCII: <Mark>любой ASCII-текст — уже правильный UTF-8</Mark>. Кириллица — 2 байта, знак рубля — 3, скрипичный ключ и большинство эмодзи — 4.

Второе свойство — служебные биты: продолжающий байт `10…` не может стоять первым в символе, а после `110…` обязан идти продолжающий. Поэтому случайные байты почти никогда не складываются в правильный UTF-8, и Python сразу замечает ошибку.

## Кракозябры: байты целы, неверна кодировка

<Term id="mojibake">Кракозябры</Term> — текст, прочитанный не той кодировкой, в которой записан. Байты при этом не испорчены. По их виду часто можно назвать пару «записали в X — прочитали как Y»:

<div className="table-scroll">

| Записали | Прочитали как | «привет» превращается в |
|---|---|---|
| UTF-8 | cp1251 | `РїСЂРёРІРµС‚` — много Р и С |
| UTF-8 | cp866 | `╨┐╤А╨╕╨▓╨╡╤В` — рамки псевдографики |
| cp1251 | UTF-8 | `UnicodeDecodeError` |

</div>

Почему в первой строке столько «Р» и «С»? У кириллицы в UTF-8 первый байт — `d0` или `d1`, а в cp1251 это и есть «Р» и «С». Каждая буква дала пару «Р + что-то» или «С + что-то».

## Ошибка или тихий мусор

В последней строке таблицы не кракозябры, а ошибка. В cp1251 символ есть у каждого байта, кроме `0x98`, поэтому почти любые байты читаются без ошибки — просто получается мусор. (Помните, слово с «И» падало даже при чтении как cp1251? «И» в UTF-8 — `d0 98`.) А UTF-8 строгий: служебные биты должны сходиться. Предскажите, сколько знаков «�» напечатает последняя строка программы:

```python
data = "привет".encode("cp1251")
try:
    print(data.decode("utf-8"))
except UnicodeDecodeError as e:
    print(e)
print(data.decode("utf-8", errors="replace"))
```

```
'utf-8' codec can't decode byte 0xef in position 0: invalid continuation byte
������
```

Байт `ef` (буква «п» в cp1251) — это `11101111`: он обещает символ из трёх байтов, но следующий `f0` не продолжающий — не начинается с `10`. Отсюда «invalid continuation byte». С `errors="replace"` ошибки нет: каждый неразобранный байт — здесь все шесть — заменён на «�», и исходные байты на этих местах **потеряны**. <Mark>Кракозябры без «�» и «?» — не порча: байты целы, и текст можно вернуть.</Mark>

## Как вернуть текст

Раз байты целы, достаточно пройти путь назад: снова получить байты той кодировкой, которой текст по ошибке прочитали, и прочитать их правильной.

```python
broken = "РїСЂРёРІРµС‚"
print(broken.encode("cp1251").decode("utf-8"))
```

```
привет
```

Если пара неизвестна, перебирают варианты; программы, «угадывающие» кодировку, делают то же по статистике символов и ошибаются, особенно на коротких текстах. Надёжно одно: знать кодировку файла и указывать её в `encoding`, например `open("sales.csv", encoding="cp1251")` для выгрузки из 1С. С Python 3.15 `open` без `encoding` везде читает UTF-8, но файл в cp1251 от этого сам не прочитается.

## BOM — метка в начале файла

Вы уже встречали CSV из Excel, где первый заголовок «прилипал» к невидимому знаку, а помогал `encoding="utf-8-sig"`. Теперь его видно:

```python
data = "дата".encode("utf-8-sig")
print(data.hex(" "))
print(repr(data.decode("utf-8")), repr(data.decode("utf-8-sig")))
```

```
ef bb bf d0 b4 d0 b0 d1 82 d0 b0
'\ufeffдата' 'дата'
```

Три байта `ef bb bf` — это <Term id="bom">BOM</Term> (byte order mark, «метка порядка байтов»): символ U+FEFF, в выводе — `\ufeff`. Название — из UTF-16, где метка показывает порядок байтов; в UTF-8 порядок один, и метка — только подпись «файл в UTF-8». Стандарт её не требует, и многие программы Linux на ней спотыкаются. `utf-8-sig` метку убирает.

## Одна буква — две кодовые точки

«й» можно записать одной кодовой точкой U+0439 — или двумя: «и» и отдельный знак над ней, кратку, U+0306. На экране они одинаковы, а для Python это разные строки: поиск «й» в таком тексте ничего не найдёт. Приводят их к одному виду **нормализацией** — функцией `unicodedata.normalize` (Unicode HOWTO, «Comparing Strings»):

```python
import unicodedata
one = unicodedata.normalize("NFC", "й")
two = unicodedata.normalize("NFD", "й")
print(len(one), len(two), one == two)
```

```
1 2 False
```

Форма `"NFC"` собирает символ в одну кодовую точку, где это возможно, `"NFD"` разбирает. Заодно видно: `len` считает кодовые точки, а не буквы, какими их видит человек. С эмодзи нормализация не поможет: флаг страны — две кодовые точки, и `len` даст 2.

## Наследство пишущей машинки

На пишущей машинке новая строка — два действия: вернуть каретку к левому краю и сдвинуть бумагу. Отсюда два управляющих символа ASCII: «возврат каретки» CR (carriage return, `\r`, номер 13) и «перевод строки» LF (line feed, `\n`, номер 10).

<Term id="line-ending">Конец строки</Term> в текстовом файле в разных ОС принято записывать по-своему: программы Windows обычно пишут два байта `\r\n` (CRLF), Linux и macOS — один `\n` (LF). Это не ошибка Windows, а такая же договорённость, как кодировка: `\r\n` — стандартный конец строки в сетевых протоколах и в формате CSV.

## Python прячет разницу — пока его не попросят

Буква `b` (`"wb"`, `"rb"`) открывает файл **в двоичном режиме**: без кодировки и без обработки, `write` принимает `bytes`, `read` возвращает `bytes`. Запишем файл с концами строк Windows и прочитаем трижды. Предскажите, что выведут три `print`, — потом сверьтесь:

```python
with open("win.txt", "wb") as f:
    f.write("хлеб\r\nсыр\r\n".encode("utf-8"))

with open("win.txt", "rb") as f:
    print(f.read())
with open("win.txt", encoding="utf-8") as f:
    print(f.readlines())
with open("win.txt", encoding="utf-8", newline="") as f:
    print(f.readlines())
```

```
b'\xd1\x85\xd0\xbb\xd0\xb5\xd0\xb1\r\n\xd1\x81\xd1\x8b\xd1\x80\r\n'
['хлеб\n', 'сыр\n']
['хлеб\r\n', 'сыр\r\n']
```

В текстовом режиме Python при чтении превращает и `\r\n`, и `\n` в `\n`, а при записи делает обратное: `\n` становится концом строки той ОС, где работает программа, — на Windows `\r\n`. С `newline=""` Python ничего не меняет.

Отсюда правило `newline=""` для модуля `csv`, которое раньше просто запоминали. При чтении концы строк разбирает сам `csv`, а при записи `csv.writer` ставит `\r\n` — без `newline=""` Python на Windows превратил бы его `\n` ещё в один `\r\n`, получилось бы `\r\r\n`, и Excel показал бы пустые строки между записями.

## Где разница вылезает

Если текст пришёл не через `open`, например по сети, и вы разбиваете его сами, `split("\n")` оставит `\r` на конце каждой строки. Выручает `splitlines()`: он понимает оба конца строки.

Скрипт для командной строки Linux, сохранённый в Windows с CRLF, падает с ошибкой `$'\r': command not found`: командная оболочка считает `\r` частью команды. Как чинить такие скрипты — в теме «Bash-скрипты — переменные, условия, циклы».
