## Откуда команда берёт текст и куда его пишет

В журнале сервиса за ночь 50 000 строк. Сколько среди них ошибок? Какая встречается чаще всего? Считать глазами в `less` — не выход: хватит одной строки команд, но сначала нужно понять, откуда команды читают текст и куда пишут результат.

<Theorem kind="definition" title="Стандартные потоки"
  formal="При запуске программы для неё уже открыты три потока: стандартный ввод (stdin) — для чтения входных данных, стандартный вывод (stdout) — для обычного вывода, стандартный поток ошибок (stderr) — для диагностических сообщений. Их номера — 0, 1 и 2."
  source="POSIX.1-2017, System Interfaces, 2.5 «Standard I/O Streams» (пересказ); man7.org, stdin(3)">

<Term id="standard-stream">Стандартные потоки</Term> — три потока данных, которые процесс получает при запуске: из stdin он читает, в stdout пишет результат, в stderr — ошибки и предупреждения. Когда вы запускаете команду в терминале, все три подключены к нему: читают с клавиатуры, пишут на экран. Поэтому ошибки и результат на экране перемешаны, хотя идут разными путями.

</Theorem>

«Поток» здесь — не поток выполнения из темы о процессах. Там поток (thread) — последовательность инструкций внутри процесса, здесь поток (stream) — последовательность байтов: в него пишут с одного конца и читают с другого. Дальше в теме «поток» значит только stream.

Ваши программы на Python уже работали с этими потоками: `input()` читает строку из stdin, `print()` пишет в stdout, а трассировка необработанного исключения уходит в stderr. Зачем ошибкам отдельный поток, станет ясно, когда вывод отправится в файл.

## Текст на входе — текст на выходе

Команды этой страницы называют <Term id="filter">фильтрами</Term>: они читают текст, преобразуют его и печатают результат в stdout. Текст берут из файлов, названных в аргументах, а если файла нет — из stdin. Без файла и в обычном терминале stdin — клавиатура: команда ждёт ввода, и кажется, что она зависла. Закончить ввод — Ctrl+D, прервать команду — Ctrl+C.

## grep — строки по образцу

`grep ОБРАЗЕЦ файл` печатает строки, где есть образец. Флаги: `-i` — без учёта регистра, `-v` — строки *без* образца, `-n` — с номерами строк, `-c` — только число строк, `-w` — образец целым словом, `-r` — во всех файлах папки и вложенных (`grep -rn learning_rate src` — где в проекте упоминается настройка).

```text
student@forge:~$ grep ERROR app.log
09:01 ERROR db timeout
09:03 ERROR disk full
09:04 ERROR db timeout
student@forge:~$ grep -c -i error app.log
4
```

Образец — регулярное выражение. Точка, `*`, `^`, `$`, `[0-9]` работают как в модуле `re`; `+`, `?` и `|` — только с `grep -E`, а `\d` нет — пишите `[0-9]`.

<Callout kind="warning" title="Ловушка: grep ищет подстроку, а не слово">
`grep cat` найдёт и `cat`, и `concatenate`. Нужно только слово — `grep -w cat`.
</Callout>

## wc, head, tail

`wc` считает строки, слова и байты; `wc -l` — только строки. Точнее, `-l` считает символы перевода строки: если в конце последней строки нет `\n`, она не попадёт в счёт. `head -n 5` — первые 5 строк, `tail -n 5` — последние; без `-n` берут по 10. `head -n 1 sales.csv` покажет заголовок таблицы. `tail -f train.log` не завершается, а показывает новые строки по мере записи — так следят за обучением модели; выход — Ctrl+C.

## sort и uniq

`sort` упорядочивает строки и по умолчанию сравнивает их как текст, поэтому `10` окажется раньше `9` — та же ловушка, что у `sorted` для строк в Python. Числа сортирует `sort -n`, обратный порядок — `-r`. Порядок букв зависит от языковых настроек системы. В Ubuntu по умолчанию (C.UTF-8 — так в WSL и на серверах) строки сравниваются по кодам символов, как в `sorted` в Python: заглавные раньше строчных, `Zeta` раньше `apple`. С русскими или английскими настройками рабочего стола порядок бывает другим — почти без учёта регистра.

```text
student@forge:~$ sort nums.txt
10
100
25
9
student@forge:~$ sort -n nums.txt
9
10
25
100
```

`uniq` убирает повторы, но <Mark>только соседние</Mark>: в `Омск, Казань, Омск` он ничего не уберёт. Поэтому перед `uniq` почти всегда стоит `sort`. `uniq -c` пишет перед строкой, сколько раз она повторилась подряд.

Попробуйте: сколько строк с `error` без учёта регистра, какие строки без `INFO`, первые две строки журнала, `uniq -c cities.txt` и `sort cities.txt`.

## Вывод — в файл

Оболочка может до запуска команды подключить её потоки не к терминалу, а к файлу. Это <Term id="redirection">перенаправление</Term> (redirection):

- `команда > файл` — stdout в файл; файла нет — создастся, есть — <Mark>`>` сначала очищает его</Mark>;
- `команда >> файл` — stdout в конец файла, старое содержимое остаётся;
- `команда < файл` — stdin из файла: `wc -l < app.log` печатает только число — имени файла `wc` не знает, он читает поток;
- `команда 2> файл` — stderr в файл (2 — номер потока ошибок).

Знакомая по файлу зависимостей строка `python3 -m pip freeze > requirements.txt` — это перенаправление: `pip freeze` печатает список пакетов в stdout, а `>` направляет его в файл.

Предскажите, что покажет каждый `cat`, потом нажимайте «Следующая команда».

<Shell files={{"app.log": "09:00 INFO start\n09:01 ERROR db timeout\n09:02 INFO login anna\n09:03 ERROR disk full\n09:04 ERROR db timeout\n09:07 WARN slow query\n09:08 error disk full\n"}} script={["grep ERROR app.log > errors.txt", "cat errors.txt", "grep WARN app.log > errors.txt", "cat errors.txt", "grep ERROR app.log >> errors.txt", "cat errors.txt", "wc -l < errors.txt"]} />

Второй `>` стёр найденные ошибки и записал одно предупреждение; `>>` дописал ошибки в конец.

## Ошибки идут мимо

`>` перенаправляет только stdout. Ошибки по-прежнему идут на экран:

```text
student@forge:~$ cat sales.csv nope.csv > all.txt
cat: nope.csv: No such file or directory
student@forge:~$ cat all.txt
city,amount
Омск,10
```

В этом и смысл отдельного потока: результат уходит в файл или дальше в обработку, а ошибку человек видит сразу, и она не портит данные. Так же `python3 report.py > out.txt` запишет в файл вывод `print`, а трассировка останется на экране.

Собрать оба потока в один файл — `> all.txt 2>&1`: «stdout в файл, а поток 2 — туда же, куда сейчас идёт поток 1». Оболочка разбирает перенаправления слева направо, поэтому `2>&1` пишут после `>`. Ненужный вывод выбрасывают в `/dev/null` — особый файл, который принимает любые данные и ничего не хранит: `cat sales.csv nope.csv 2> /dev/null` покажет таблицу без сообщения об ошибке.

<Callout kind="warning" title="Ловушка: sort f > f">
Хотели отсортировать файл на месте: `sort nums.txt > nums.txt`. Оболочка готовит перенаправление **до** запуска `sort` и очищает `nums.txt`. `sort` читает уже пустой файл — данных больше нет. Правильно — через другой файл: `sort nums.txt > sorted.txt`, затем `mv sorted.txt nums.txt`. У самого `sort` для этого есть флаг: `sort -o nums.txt nums.txt`.
</Callout>

## Выход одной команды — вход другой

Сколько ошибок в журнале? Можно сохранить найденное в файл и посчитать строки в нём. Но промежуточный файл не нужен: знак `|` соединяет stdout одной команды со stdin следующей.

```text
student@forge:~$ grep ERROR app.log | wc -l
3
```

<Theorem kind="definition" title="Конвейер"
  formal="Конвейер (pipeline) — последовательность команд, разделённых символом |. Стандартный вывод каждой команды соединяется каналом (pipe) со стандартным вводом следующей. Каждая команда конвейера выполняется в своём процессе; оболочка ждёт завершения всех."
  source="GNU Bash Reference Manual, 3.2.3 «Pipelines» (пересказ); POSIX.1-2017, Shell Command Language, 2.9.2 «Pipelines»">

<Term id="pipeline">Конвейер</Term> (в работе говорят «пайп», от pipe — «труба») — цепочка команд, где каждая получает на вход то, что напечатала предыдущая. `grep` выбрал строки с ошибками и печатает их не на экран, а в канал; `wc -l` читает канал и считает строки — файла ему не нужно, потому что фильтр без файла читает stdin.

</Theorem>

Два следствия из определения:

- **Команды конвейера работают одновременно**, каждая — своим процессом. `grep` ещё читает журнал, а `wc` уже считает пришедшие строки. Файла посередине нет — по каналу идёт поток байтов.
- **В канал попадает только stdout.** Ошибки по-прежнему идут на экран.

Ваша программа на Python, которая читает `input()` и печатает `print()`, — тоже фильтр, и её можно поставить в конвейер.

Из какого города больше всего заказов? Соберите ответ по шагам: перед каждой командой предскажите её вывод.

## Поиск файлов в дереве

`grep` ищет внутри файлов, а `find` — сами файлы: `find ГДЕ УСЛОВИЯ` обходит папку со всеми вложенными. `-name` задаёт шаблон имени, `-type f` оставляет только файлы, `-type d` — только папки. Условия `find` — целые слова с одним минусом, их не склеивают, как короткие флаги.

```text
student@forge:~$ find . -name '*.csv'
./data/jan.csv
./data/old/dec.csv
./sales.csv
```

Файлы идут в порядке обхода, а не по алфавиту. Шаблон здесь в кавычках не случайно. Без них `*.csv` раскроет оболочка, как раскрывала его для `rm`: если в текущей папке есть только `sales.csv`, `find` получит `-name sales.csv` и найдёт лишь файлы с этим именем, а если подходящих файлов в папке несколько — откажется работать с ошибкой `paths must precede expression`. Кавычки доносят шаблон до `find`, и он сам сверяет его с каждым именем в дереве.

Сколько всего CSV в проекте — `find . -name '*.csv' | wc -l`.
