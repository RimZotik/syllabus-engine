## ps: что сейчас работает

Вы знаете, что запущенная программа — процесс со своим номером, PID. В Windows их показывает Диспетчер задач, в Linux — команда `ps` (process status). Все процессы машины показывает `ps aux` (флаги без минуса — старая, но живая запись):

```text
student@forge:~$ ps aux
USER         PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
root           1  0.0  0.3 167804 12900 ?        Ss   Nov20   0:02 /sbin/init
student     2210  0.0  0.1  11200  5100 pts/0    Ss   08:10   0:00 -bash
student     3001 99.7  0.2  68919  9000 ?        R    07:50  29:54 hog
student     4100  0.0  0.1  13900  4300 pts/0    R+   08:20   0:00 ps aux
```

Это четыре строки из длинного списка. Главные столбцы:

- `USER` — от чьего имени работает процесс; `%CPU` и `%MEM` — доля процессора и памяти; `TIME` — сколько процессорного времени он уже израсходовал; `COMMAND` — как процесс запущен. `-bash` с минусом — оболочка, открытая при входе.
- `TTY` — терминал процесса: `pts/0` — первое окно, `?` — процесс не привязан к терминалу.
- `STAT` — состояние: `R` — выполняется или ждёт очереди к ядру процессора, `S` — спит, ждёт события (клавиши, данных, таймера), `T` — остановлен, `D` — ждёт диска и не прерывается даже `kill -9`, пока ожидание не кончится. Значки после буквы, вроде `s` и `+`, пока можно не читать.

## Родители и дети

Процесс запускает другой процесс: на `ls` оболочка создаёт процесс `ls` и ждёт его завершения. Запустивший — **родитель**, его номер — PPID (parent PID); его показывает третий столбец `ps -ef`. Так все процессы складываются в дерево; в корне — процесс с PID 1, его запускает ОС при загрузке.

Искать процесс по имени удобнее командой `pgrep`: `pgrep -l hog` печатает номер и имя. Имя процесса — имя программы: у `python3 train.py` это `python3`, поэтому `pgrep train.py` ничего не найдёт. Искать по всей строке запуска — `pgrep -af train.py`. Классическое `ps aux | grep hog` покажет ещё и строку самого `grep`: он тоже процесс.

## Живая таблица

`ps` — снимок на одно мгновение. `top` обновляет таблицу сам — по умолчанию раз в 3 секунды — и ставит наверх тех, кто больше всех занимает процессор. Сверху — сводка о загрузке процессора и памяти, ниже — знакомые столбцы. Выход — `q`, сортировка по памяти — `M`, обратно по процессору — `P`.

Наберите `top` и найдите, кто съел процессор:

<Mark>`%CPU` в строке процесса считается от одного ядра процессора:</Mark> 100 — процесс занял одно ядро целиком. На восьми ядрах это восьмая часть машины. Однопоточная программа выше 100 не поднимется — её единственный поток выполнения в каждый момент занимает одно ядро; многопоточная может показать 300 или 700. Долю всего процессора показывает строка `%Cpu(s)` сводки.

## Как остановить процесс

Процессу не скажешь «остановись» словами: ОС передаёт ему сигнал.

<Theorem kind="definition" title="Сигнал"
  formal="Сигнал — уведомление процесса о событии, которое ОС доставляет в любой момент его работы. У каждого сигнала есть действие по умолчанию: завершить процесс, остановить, продолжить или проигнорировать. Процесс может назначить сигналу свой обработчик или игнорировать его — кроме SIGKILL и SIGSTOP, которые нельзя ни перехватить, ни игнорировать."
  source="man7.org, signal(7) (пересказ); IEEE Std 1003.1 (POSIX), заголовок signal.h; W. Shotts, «The Linux Command Line», гл. 10 «Processes»">

<Term id="signal">Сигнал</Term> — номер события, который ОС передаёт процессу: «тебя прерывают», «пора завершаться», «тебя убивают». Программа может ответить по-своему — например, сохранить работу перед выходом. Два сигнала программе не подвластны: завершение SIGKILL и остановку SIGSTOP выполняет сама ОС.

</Theorem>

| Сигнал | Номер | Как послать | Что делает по умолчанию |
|---|---|---|---|
| SIGINT | 2 | `Ctrl+C` в терминале | прерывает программу |
| SIGTERM | 15 | `kill PID` | просит завершиться |
| SIGKILL | 9 | `kill -9 PID` | ОС снимает процесс сразу |
| SIGTSTP | 20 | `Ctrl+Z` в терминале | приостанавливает |
| SIGHUP | 1 | закрытие терминала | завершает |

## Ctrl+C и Python

Вы уже останавливали бесконечный цикл клавишами `Ctrl+C` и знаете, что голый `except` ловит даже их. Теперь понятно почему: Python превращает SIGINT в исключение `KeyboardInterrupt`. Без обработчика программа падает с трассировкой. Вот `count.py`, печатающий раз в секунду следующее число, и `Ctrl+C` на второй секунде (на своём компьютере; `^C` — так терминал показывает нажатие):

```text
student@forge:~$ python3 count.py
1
2
^CTraceback (most recent call last):
  File "/home/student/count.py", line 6, in <module>
    time.sleep(1)
KeyboardInterrupt
```

В терминале `Ctrl+C` — сигнал, а не «копировать»; копирует в терминале Ubuntu `Ctrl+Shift+C`.

## kill — послать сигнал

Название обманчиво: <Mark>`kill` не убивает, а посылает сигнал</Mark>, по умолчанию SIGTERM — «пожалуйста, завершись». Программа с обработчиком SIGTERM допишет файл и выйдет. SIGKILL (`kill -9`) обработать нельзя: ОС снимает процесс на месте, и начатый файл так и останется оборванным. Поэтому сначала `kill PID`, несколько секунд ожидания, и только если процесс жив — `kill -9 PID`.

Python сам SIGTERM не обрабатывает: в отличие от `Ctrl+C`, исключения не будет, `finally` не выполнится, и программа завершится так же резко, как от `kill -9`. Свой обработчик ставят модулем `signal`.

Чужой процесс без `sudo` не остановить: `bash: kill: (1) - Operation not permitted`.

В тренажёре `hog` занимает процессор, `worker` по SIGTERM записывает в `state.txt` слово `saved`, `stubborn` игнорирует SIGTERM. Предскажите, что покажет каждая команда:

<Shell processes={[{name: "hog", behavior: "busy"}, {name: "worker", behavior: "cleanup", file: "state.txt"}, {name: "stubborn", behavior: "ignore_term"}]} script={["pgrep -l hog", "kill 3001", "pgrep -l hog", "pgrep -l worker", "kill 3002", "cat state.txt", "pgrep -l stubborn", "kill 3003", "pgrep -l stubborn", "kill -9 3003", "pgrep -l stubborn"]} />

`pgrep` ничего не печатает, если такого процесса нет. Теперь нажмите «Сбросить» и пошлите процессу `worker` сразу `kill -9 3002`: обработчик не запустится, и `state.txt` останется пустым. Так же оборвётся на полуслове файл, который пишет настоящая программа.

## Терминал не обязан ждать

Пока работает команда, оболочка ждёт её завершения и новых команд не принимает: команда идёт **на переднем плане**. Знак `&` в конце запускает команду **в фоне**: оболочка печатает номер задания и PID и сразу возвращает приглашение.

<Term id="background-job">Фоновое задание</Term> (job; в названии темы — фоновая задача) — команда, которую оболочка запустила, не дожидаясь её завершения. Задания этого окна показывает `jobs`, номер задания пишут со знаком `%`: `kill %1`. Для опытов удобна `sleep 300` — она просто ждёт 300 секунд.

`Ctrl+Z` посылает команде на переднем плане SIGTSTP: она **приостанавливается**, но не завершается — процесс остаётся в памяти со статусом `Stopped`. Дальше есть выбор: `fg` вернёт её на передний план, `bg` продолжит в фоне.

Попробуйте: на `sleep 100` нажмите `Ctrl+Z`, дальше — свои `jobs`, `bg`, `fg` и `Ctrl+C`.

<Shell script={["sleep 300 &", "jobs", "kill %1", "sleep 100"]} />

Задания живут вместе с окном: закроете терминал — оболочка получит SIGHUP и передаст его заданиям, и они завершатся. Долгое обучение на сервере запускают так, чтобы оно пережило выход:

```text
student@forge:~$ nohup python3 -u train.py > train.log 2>&1 &
```

`nohup` — запустить команду так, чтобы SIGHUP её не завершил. `-u` велит Python писать вывод сразу, а не копить, — иначе `train.log` долго будет пустым. Службы, которые работают постоянно, разберём в разделе «Свой сервер».

## Как команда сообщает итог

Команда может напечатать что угодно, но скрипту и другим программам нужен простой ответ: получилось или нет.

<Theorem kind="definition" title="Код возврата"
  formal="Код возврата (exit status) — число от 0 до 255, которое процесс передаёт родителю при завершении. Для оболочки команда с кодом 0 завершилась успешно, с ненулевым — неудачно. Если команда завершена сигналом с номером N, bash использует код 128 + N; не найденная команда даёт 127, найденная, но не исполняемая, — 126."
  source="GNU Bash Reference Manual, 3.7.5 «Exit Status» (пересказ); IEEE Std 1003.1 (POSIX), Shell Command Language, 2.8.2 «Exit Status for Commands»">

<Term id="exit-status">Код возврата</Term> (exit code) — число, которым процесс сообщает, чем закончился: 0 — успех, всё остальное — неудача, и разные числа означают разные причины. Код последней команды хранит `$?`; у конвейера это код его последней команды.

</Theorem>

<Callout kind="warning" title="Ловушка: 0 — это успех">
В Python 0 ложен, а в оболочке код 0 значит «получилось». Ошибок может быть много разных, а успех один — ему и отдали 0.
</Callout>

Три новых обозначения для опыта ниже:

- `;` разделяет команды в одной строке: сначала первая, потом вторая — что бы ни случилось с первой;
- `&&` выполняет следующую команду, только если предыдущая вернула 0, `||` — только если не 0;
- `grep -q` (quiet — «тихо») ничего не печатает, только возвращает код.

Предскажите вывод каждой строки:

<Shell files={{"todo.txt": "купить молоко\nпозвонить маме\n", "app.log": "INFO start\nINFO done\n"}} script={["ls todo.txt; echo $?", "ls nope.txt; echo $?", "grep -q молоко todo.txt; echo $?", "grep -q хлеб todo.txt; echo $?", "grep -c ERROR app.log; echo $?", "ls nope.txt || echo 'не вышло'", "nosuchcmd; echo $?"]} />

У `grep` код 1 — «не нашёл», а не ошибка; настоящая ошибка, например нет файла, — 2. `grep -c` печатает `0` и при этом возвращает 1: вывод и код — разные вещи.

## Код возврата вашей программы

Python завершается с кодом 0, если программа дошла до конца; с кодом 1 — если упала с необработанным исключением; со своим кодом — по `sys.exit(3)`. После `Ctrl+C` код — 130, то есть 128 + 2: процесс завершён сигналом SIGINT.

На этом построены автоматические проверки: тесты упали — код не 0 — дальше дело не идёт. Скрипты, которые проверяют `$?`, — в теме «Bash-скрипты — переменные, условия, циклы».

  options={["0, а затем «ошибок нет»", "Только «ошибок нет»", "0, а затем «есть ошибки»: grep отработал без сбоев", "Только 0: после grep строка останавливается"]}
