## Обещанное: задать переменную снаружи

Вы читали переменные окружения из Python: `os.environ.get("SHOP_DISCOUNT", "0")`. Окружение — набор строк вида `имя=значение`, который процесс получает от родительского процесса при запуске. До сих пор вы задавали его в самой программе — теперь из терминала, как на сервере.

Чтобы получить значение переменной, пишут `$ИМЯ`:

```text
student@forge:~$ echo $HOME
/home/student
student@forge:~$ echo "Я — $USER, папка $PWD"
Я — student, папка /home/student
```

Значение на место `$ИМЯ` подставляет оболочка до запуска команды — так же, как раскрывает шаблоны `*`: `echo` получает уже готовый текст. Вы уже знаете, что одинарные кавычки отключают особый смысл символов: `echo '$HOME'` напечатает `$HOME`, а в двойных кавычках подстановка работает.

Всё окружение печатают `env` и `printenv`, одну переменную — `printenv HOME`. Почти всегда есть `HOME` (домашняя папка), `USER` (имя пользователя), `PWD` (текущая папка) и `PATH` — где искать команды, о нём через страницу.

## Для одного запуска

Чтобы задать переменную только для одной команды, её пишут перед командой:

```text
student@forge:~$ MODE=test python3 app.py
```

`app.py` увидит `os.environ["MODE"] == "test"`, а после его завершения переменной в терминале нет. Пробелы вокруг `=` ставить нельзя: `MODE = test` оболочка поймёт как команду `MODE` с аргументами — `bash: MODE: command not found`.

## Видит ли программа вашу переменную

Задайте переменную отдельной строкой и запустите скрипт, который её печатает, — по пути, как скрипт выкладки в теме о правах: `./hello.sh`. Предскажите, что он напечатает, потом нажимайте «Следующая команда»:

<Shell
  files={{"hello.sh": {content: "#!/bin/bash\necho \"скрипт видит MODE=$MODE\"\n", mode: "755"}}}
  script={["cat hello.sh", "MODE=test", "echo $MODE", "./hello.sh", "export MODE", "./hello.sh", "MODE=prod ./hello.sh", "echo $MODE"]}
/>

Скрипт — отдельный процесс — переменную оболочки не видит, пока не выполнен `export`.

<Theorem kind="rule" title="Наследование окружения"
  formal="При запуске программы ей передаётся окружение — список пар «имя=значение». Запущенные оболочкой команды наследуют окружение, составленное из переменных, помеченных для экспорта; export помечает переменную для экспорта, и она передаётся всем командам, запущенным после этого. Присваивание перед именем команды добавляет переменную только в окружение этой команды."
  source="GNU Bash Reference Manual, 3.7.4 «Environment» и 4.1 «Bourne Shell Builtins», export (пересказ); W. Shotts, «The Linux Command Line», гл. 11 «The Environment»">

У оболочки два вида переменных. <Term id="shell-variable">Переменная оболочки</Term> (`MODE=test`) живёт только внутри процесса bash. Переменная окружения — та, что помечена `export`: её **копию** получает каждая программа, запущенная из этой оболочки. Можно сразу: `export MODE=test`.

</Theorem>

Слово «копию» здесь главное: дочерний процесс может менять свой экземпляр как угодно, родитель этого не увидит:

- Если Python-программа выполнит `os.environ["MODE"] = "prod"`, переменная терминала не изменится: ваша оболочка — её родитель.
- Скрипт, где написано `export MODE=dev` и `cd /tmp`, ничего не меняет в вашем окне: и окружение, и текущая папка — свойства процесса, а скрипт работает в отдельном процессе.
- Каждое окно терминала — свой процесс bash: `export` в одном окне не виден в другом и пропадает с закрытием окна.

<Callout kind="warning" title="Ловушка: «я же задал переменную»">
`DB_PASSWORD=secret` без `export`, затем `python3 app.py` — и `os.environ["DB_PASSWORD"]` падает с `KeyError`, хотя `echo $DB_PASSWORD` печатает `secret`: в окружение программы переменная не попала.
</Callout>

</Page>

## Откуда берётся ls

Вы набираете `ls`, но `ls` — не встроенная команда оболочки, а программа, файл на диске: `which ls` отвечает `/usr/bin/ls`. Найти файл по одному имени оболочке помогает переменная окружения `PATH`.

<Theorem kind="definition" title="PATH"
  formal="Переменная окружения PATH — последовательность путей к каталогам, разделённых двоеточием. Когда команда задана именем без косой черты, файл ищется в этих каталогах по порядку, от первого к последнему, и выполняется первый найденный. Если имя содержит косую черту, поиск по PATH не выполняется."
  source="IEEE Std 1003.1 (POSIX), Base Definitions, 8.3 «Other Environment Variables», PATH (пересказ); GNU Bash Reference Manual, 3.7.2 «Command Search and Execution»">

<Term id="path-variable">`PATH`</Term> — список папок, в которых оболочка ищет программу по имени. Ищет слева направо и останавливается на первой находке. Нет ни в одной папке — `command not found` и код возврата 127.

</Theorem>

```text
student@forge:~$ echo $PATH
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games:/snap/bin
```

Так выглядит `PATH` в Ubuntu 24.04; в тренажёре он короче, в WSL длиннее — туда добавлены папки Windows. Следствия определения:

- **Порядок решает.** Если `python3` есть и в `/usr/local/bin`, и в `/usr/bin`, запустится первый. `which python3` покажет, какой файл найдёт поиск по `PATH` сейчас, — а не где программа «установлена».
- **Текущей папки в `PATH` нет.** Поэтому свой скрипт запускают с путём: `./deploy.sh`, а не `deploy.sh`. Это защита: иначе файл с именем `ls`, подброшенный в общую папку, выполнился бы вместо настоящего.
- **Встроенные команды оболочка проверяет раньше, чем `PATH`.** `type`, знакомая по команде `cd`, знает обо всём. `type -a echo` перечислит по порядку всё, что откликается на имя: `echo is a shell builtin`, потом файлы `/usr/bin/echo` и `/bin/echo`. Запустится первое — встроенная команда, хотя `which echo` назовёт файл.

## Своя папка в PATH

Свои программы собирают в папку и добавляют её в `PATH`, сохранив прежний список:

```text
student@forge:~$ export PATH="$HOME/tools/bin:$PATH"
```

`$PATH` справа подставит старое значение, поэтому вся строка — «новая папка, двоеточие, всё, что было». Новая папка в начале — ваша версия программы победит системную; в конце — наоборот. Попробуйте:

<Shell
  files={{"tools/bin/report": {content: "#!/bin/bash\necho 'отчёт готов'\n", mode: "755"}}}
  script={["echo $PATH", "which ls", "type cd", "report", "tools/bin/report", "export PATH=\"$HOME/tools/bin:$PATH\"", "echo $PATH", "which report", "report"]}
/>

<Callout kind="warning" title="Ловушка: PATH без $PATH">
`export PATH=$HOME/tools/bin` заменит весь список одной папкой — и `ls`, `nano`, `python3` станут `command not found`. Программы при этом на месте: `/usr/bin/ls` по полному пути работает. Починить — вернуть стандартный список (`export PATH=/usr/local/bin:/usr/bin:/bin`) или открыть новое окно: испорченный `PATH` живёт только в этом.
</Callout>

  options={["pytest — из .local/bin, python3 — из /usr/bin", "Обе — из /usr/bin: системные папки просматриваются первыми", "pytest — из /usr/bin, потому что там же python3, который его запускает", "pytest — оба по очереди, python3 — из /usr/bin"]}

## Файл, который bash читает при запуске

Переменная из `export` живёт до закрытия окна. Чтобы настройка была в каждом новом окне, её записывают в <Term id="bashrc">`~/.bashrc`</Term> — скрытый файл в домашней папке, который bash выполняет при старте каждого окна терминала.

Строку дописывают в конец редактором — `nano ~/.bashrc` — или одной командой:

```text
student@forge:~$ echo 'export PATH="$HOME/tools/bin:$PATH"' >> ~/.bashrc
```

Одинарные кавычки здесь обязательны: в файл должен попасть сам текст `$PATH`, чтобы `PATH` собирался заново при каждом запуске, а не застыл в сегодняшнем виде. И `>>`, а не `>`: одна стрелка затёрла бы весь файл.

Файл прочитан при старте окна, поэтому в уже открытом окне правка сама не подействует. Два способа:

- открыть новое окно — кнопка «Новое окно терминала» в тренажёре;
- выполнить `source ~/.bashrc`: команда `source` выполняет файл **в текущей оболочке**, а не в дочернем процессе, поэтому его `export` меняют это окно.

<Shell
  files={{"tools/bin/report": {content: "#!/bin/bash\necho 'отчёт готов'\n", mode: "755"}}}
  script={["tail -n 3 ~/.bashrc", "echo 'export PATH=\"$HOME/tools/bin:$PATH\"' >> ~/.bashrc", "tail -n 1 ~/.bashrc", "report", "source ~/.bashrc", "report"]}
/>

`~/.bashrc` читают только оболочки, в которых вы набираете команды. Скрипты, запущенные по расписанию, и службы его не читают — это встретится в разделе «Свой сервер».

## Какой редактор откроется

Программы, которым нужен редактор, — например, Git, когда просит написать сообщение коммита, — узнают его из переменных окружения: сначала `VISUAL`, потом `EDITOR`. Если обе пусты, берётся редактор по умолчанию, и это может оказаться vim. Чтобы всегда открывался nano, в `~/.bashrc` добавляют строки `export VISUAL=nano` и `export EDITOR=nano`.

API-ключи и пароли в `~/.bashrc` не пишут: файл легко показать или скопировать вместе с настройками. Да и набранная команда `export API_KEY=…` остаётся в истории оболочки — в файле `~/.bash_history`.

## Активация — это PATH

Вы включали виртуальное окружение, и после этого `python` в окне означал Python окружения. Теперь видно, как это устроено. Главное, что делает скрипт `activate`: задаёт `VIRTUAL_ENV` — путь к папке окружения — и ставит её папку `bin` **в начало** `PATH`. Остальное — следствие правила поиска. На своём компьютере:

```text
student@forge:~/shop$ which python3
/usr/bin/python3
student@forge:~/shop$ source .venv/bin/activate
(.venv) student@forge:~/shop$ which python3
/home/student/shop/.venv/bin/python3
(.venv) student@forge:~/shop$ echo $VIRTUAL_ENV
/home/student/shop/.venv
```

`(.venv)` в приглашении тоже ставит `activate` — напоминание, что окружение включено. `deactivate` возвращает прежний `PATH`.

Отсюда и знакомые правила venv:

- Включают через `source`, а не запуском: скрипт в дочернем процессе изменил бы только свою копию `PATH`.
- Окружение включено **в одном окне**: `PATH` — переменная процесса bash этого окна.
- Активировать не обязательно: `.venv/bin/python3 app.py` — имя с косой чертой, поиск по `PATH` не нужен.
- `sudo python3` запустит системный Python даже при включённом окружении: у `sudo` свой `PATH`.

Создавать окружения через `venv` и `uv` вы будете в теме «Редактор кода и отладчик; изолированные окружения Python (uv, venv)».
