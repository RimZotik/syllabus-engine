## Строки сортируются не как даты

Даты сдачи из таблицы пришли строками. Предскажите порядок после сортировки:

```python
print(sorted(["17.05.2024", "03.06.2023", "28.02.2024"]))
```

```
['03.06.2023', '17.05.2024', '28.02.2024']
```

Строки сравниваются посимвольно, а первым в записи стоит день: «17» меньше «28», поэтому 17 мая встало раньше 28 февраля. А 2023 год оказался первым случайно — у него день «03». Посчитать «сколько дней между» со строками тоже нельзя. Нужен тип, который знает календарь.

## date и datetime

Модуль `datetime` стандартной библиотеки даёт для этого <Term id="datetime">типы `date` и `datetime`</Term>: `date` — дата (год, месяц, день), `datetime` — дата и время до микросекунд. Значения создают, передавая числа по порядку — от крупной единицы к мелкой: год, месяц, день, часы, минуты.

```python
from datetime import date, datetime

d = date(2024, 5, 17)
print(d, d.year, d.month, d.day, d.weekday())
t = datetime(2024, 5, 17, 14, 30)
print(t, t.date(), t.hour)
print(date(2024, 5, 17) < date(2024, 6, 1))
```

```
2024-05-17 2024 5 17 4
2024-05-17 14:30:00 2024-05-17 14
True
```

- `year`, `month`, `day`, `hour` — атрибуты, без скобок; `weekday()` — метод: день недели числом, **понедельник — 0**, воскресенье — 6. 17 мая 2024 года — пятница, 4. Привычный счёт с единицы даёт `isoweekday()`.
- Даты сравниваются по времени, а не по символам: раньше — меньше. Поэтому `sorted` и `max` для списка дат работают как надо. Только `date` с `datetime` не сравнивают — `TypeError`.
- Календарь проверяется при создании: `date(2023, 2, 29)` выбросит `ValueError: day is out of range for month` — 2023 год не високосный.

`date.today()` и `datetime.now()` дают сегодняшнюю дату и текущий момент по часам компьютера. В задачах их не используют — ответ зависел бы от дня запуска: «сегодня» функция получает параметром.

## Разность дат

Вычтем одну дату из другой. Предскажите обе строки вывода — вторая поездка проходит через полночь:

```python
from datetime import date, datetime

left = date(2024, 12, 31) - date(2024, 5, 17)
print(left, left.days)
trip = datetime(2024, 5, 18, 1, 15) - datetime(2024, 5, 17, 22, 40)
print(trip, trip.total_seconds() / 60)
```

```
228 days, 0:00:00 228
2:35:00 155.0
```

<Term id="timedelta">`timedelta`</Term> — тип промежутка времени: разность двух дат или двух моментов. `days` — число целых суток, `total_seconds()` — весь промежуток в секундах. Не путайте с атрибутом `seconds`: это только секунды сверх целых суток, от 0 до 86 399.

Промежуток можно прибавить к дате и получить новую дату. Високосный год `datetime` учитывает сам:

```python
from datetime import date, timedelta

print(date(2024, 5, 17) + timedelta(days=30))
print(date(2024, 2, 28) + timedelta(days=1), date(2023, 2, 28) + timedelta(days=1))
```

```
2024-06-16
2024-02-29 2023-03-01
```

<Callout kind="warning" title="Ловушка: месяц — не 30 дней">
У `timedelta` нет месяцев и лет: `timedelta(months=1)` — `TypeError`. Это не упущение. Месяц — не промежуток постоянной длины: от 28 до 31 дня. «Через месяц после 31 января» — это 29 февраля или 2 марта? Ответ зависит от правила, принятого в вашей задаче: в банке, в подписке, в расписании. `timedelta(days=30)` — это ровно 30 суток, а не месяц.
</Callout>

## Формат для обмена

«05.06.2024» в России — 5 июня, в США — 6 мая: там месяц пишут первым. Для обмена данными есть международный стандарт.

<Theorem kind="definition" title="ISO 8601"
  formal="Международный стандарт представления даты и времени. Единицы записываются от старшей к младшей: дата — ГГГГ-ММ-ДД, время — чч:мм:сс, между датой и временем — буква T; смещение от UTC указывается в конце как ±чч:мм или буквой Z для самого UTC."
  source="ISO 8601-1:2019 (пересказ); документация Python, datetime: isoformat, fromisoformat">

<Term id="iso-8601">ISO 8601</Term> — запись вида `2024-05-17T14:30:00`. Её понимают программы на любых языках и базы данных, в ней же приходят даты в JSON-ответах сайтов. Месяц и день всегда двузначные: `05`, а не `5`.

</Theorem>

Старшая единица стоит первой, а части одной длины, поэтому даты в ISO 8601 сортируются верно, даже если сравнивать их как обычные строки, — при условии, что все записи одного вида и с одним смещением. Моменты с разными смещениями сначала переводят в `datetime`.

```python
from datetime import datetime

t = datetime(2024, 5, 17, 14, 30)
print(t.isoformat())
print(datetime.fromisoformat("2024-05-17T14:30:00") == t)
print(sorted(["2024-05-17", "2023-06-03", "2024-02-28"]))
```

```
2024-05-17T14:30:00
True
['2023-06-03', '2024-02-28', '2024-05-17']
```

`isoformat()` — в строку ISO 8601, `fromisoformat(...)` — обратно. <Mark>В файлах, в том числе в CSV и JSON, дату храните в ISO 8601.</Mark> Типа «дата» в JSON нет: `json.dumps` дату не примет, а строку из `isoformat()` — примет.

## Свои форматы: strptime и strftime

Люди пишут иначе: «17.05.2024 14:30». Разобрать такую строку — `datetime.strptime(текст, формат)` (p — parse, «разобрать»), вывести дату по-своему — `t.strftime(формат)` (f — format, «оформить»). В формате коды с `%` означают части даты:

<div className="table-scroll">

| Код | Что это | Пример |
|---|---|---|
| `%d` | день | `17` |
| `%m` | **месяц** | `05` |
| `%Y` | год, четыре цифры | `2024` |
| `%H` | час, 00–23 | `14` |
| `%M` | **минуты** | `30` |
| `%S` | секунды | `00` |

</div>

При выводе (`strftime`) день, месяц, часы и минуты — всегда две цифры с нулём; при разборе (`strptime`) подойдёт и одна: «7.5.2024».

```python
from datetime import datetime

t = datetime.strptime("17.05.2024 14:30", "%d.%m.%Y %H:%M")
print(t, t.strftime("%d.%m.%Y"))
print(datetime.strptime("17.05.2024", "%d.%M.%Y"))
```

```
2024-05-17 14:30:00 17.05.2024
2024-01-17 00:05:00
```

Во втором вызове `strptime` вместо `%m` написано `%M`, и ошибки нет: «05» прочитано как пять минут, а месяц остался по умолчанию — январь. Тихая ошибка хуже громкой.

Если текст не подходит под формат («17/05/2024») или такой даты не бывает («31.02.2024»), `strptime` выбросит `ValueError`.

## «14:30» — но по чьим часам?

Заказ создан 17 мая 2024 года в 14:30. Но по чьим часам? «14:30» по часам сервера в Москве и «14:30» по часам склада в Екатеринбурге — разные моменты: в Екатеринбурге в это время на два часа позже. Время без пояса — как сумма без валюты.

<Term id="utc">UTC</Term> (Coordinated Universal Time — всемирное координированное время) — шкала, от которой отсчитывают пояса: московское время — UTC+3, екатеринбургское — UTC+5.

<Theorem kind="definition" title="Наивные и осведомлённые значения времени"
  formal="Объекты даты и времени делятся на осведомлённые (aware) и наивные (naive) — по тому, содержат ли они сведения о часовом поясе. Осведомлённый объект обозначает конкретный момент времени, не допускающий разных толкований. Наивный объект не содержит достаточно сведений, чтобы однозначно определить его место среди других моментов; что он означает — местное время, UTC или время другого пояса, — решает программа."
  source="Документация Python, datetime: Aware and Naive Objects (пересказ)">

<Term id="naive-datetime">Наивное</Term> время — без пояса: `datetime(2024, 5, 17, 14, 30)`; его атрибут `tzinfo` (сведения о поясе) — `None`. <Term id="aware-datetime">Осведомлённое</Term> — с поясом: знает смещение от UTC, поэтому обозначает один точный момент.

</Theorem>

Пояс с постоянным смещением задают так: `timezone(timedelta(hours=3))`, для UTC есть готовый пояс `timezone.utc`. Метод `astimezone` показывает тот же момент в другом поясе:

```python
from datetime import datetime, timedelta, timezone

msk = timezone(timedelta(hours=3))
ekb = timezone(timedelta(hours=5))
order = datetime(2024, 5, 17, 14, 30, tzinfo=msk)
print(order)
print(order.astimezone(timezone.utc))
print(order.astimezone(ekb))
```

```
2024-05-17 14:30:00+03:00
2024-05-17 11:30:00+00:00
2024-05-17 16:30:00+05:00
```

Три строки вывода — один момент на трёх часах.

## Наивное с осведомлённым не упорядочить

```python
from datetime import datetime, timedelta, timezone

aware = datetime(2024, 5, 17, 14, 30, tzinfo=timezone(timedelta(hours=3)))
naive = datetime(2024, 5, 17, 14, 30)
print(aware == naive)
print(aware < naive)
```

```
False
Traceback (most recent call last):
  ...
TypeError: can't compare offset-naive and offset-aware datetimes
```

`==` просто отвечает «не равны», а `<` и вычитание выбрасывают `TypeError`: Python не угадывает, в каком поясе наивное время.

<Callout kind="warning" title="Ловушка: now() — не UTC">
`datetime.now()` возвращает **наивное местное** время компьютера, а не UTC. На сервере в другом поясе тот же код даст другие часы. Правило работы: <Mark>храните и сравнивайте моменты в UTC, а в местное время переводите только для показа человеку.</Mark> Текущий момент в UTC — `datetime.now(timezone.utc)`. Старый `datetime.utcnow()` из примеров в интернете не используйте: он даёт наивное значение и устарел с Python 3.12.
</Callout>

Постоянное смещение — упрощение: где есть летнее время, в день перевода часов в сутках 23 или 25 часов. Такие правила хранит база часовых поясов, её подключает модуль `zoneinfo`: `ZoneInfo("Europe/Moscow")`. В песочнице базы нет — здесь работаем с постоянными смещениями. На Windows базу ставят пакетом `tzdata`; как ставить пакеты — в теме «Сторонние пакеты и окружение» раздела «Модули и мини-проект».
