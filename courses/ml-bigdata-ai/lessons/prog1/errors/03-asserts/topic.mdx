## Как понять, что функция верна

Ассистент написал функцию, и на одном примере она отвечает правильно. Верна ли она? Перечитывать код ненадёжно: легко не заметить ошибку на единицу или забытый пустой список. Надёжнее проверять на примерах — и повторять проверку при каждом изменении кода.

Инструмент вы знаете — `assert`: он уже поймал ошибку на единицу в `warm_days`. Лучшее сообщение — f-строка с тем, что вернула функция. Теперь научимся подбирать проверки систематически.

## Тест — это требования, записанные кодом

Проверки удобно писать **до** кода — прямо по условию задачи. Условие: «Билет в музей. Возраст — целое число лет. До 7 лет — бесплатно, от 7 до 17 лет включительно — 250 рублей, с 18 — 500 рублей». Функции ещё нет, а проверки уже есть:

```python
assert ticket_price(4) == 0
assert ticket_price(12) == 250
assert ticket_price(40) == 500
```

Это то же условие, но его проверит компьютер. Тест говорит не *как* считать, а *что* должно получиться, поэтому годится для любого кода — вашего или ассистента.

</Page>

## Три обычных случая — мало

Три проверки выше проходит и такая функция:

```python
def ticket_price(age):
    if age <= 7:
        return 0
    if age < 18:
        return 250
    return 500
```

`<=` вместо `<`: семилетнего пустят бесплатно, а он должен платить 250. Ни 4, ни 12, ни 40 этого не заметят: ошибка живёт на стыке групп.

<Theorem kind="rule" title="Какие случаи проверять"
  formal="Тестовые случаи подбирают по спецификации: входы разбивают на группы, на которых функция должна вести себя одинаково, и берут пример из каждой группы. Отдельно проверяют граничные условия (граничные случаи): значения на стыке групп, пустой список, список из одного элемента, ноль, самые маленькие и самые большие значения."
  source="J. Guttag, «Introduction to Computation and Programming Using Python», гл. «Testing and Debugging» (пересказ)">

Спецификация — описание того, что функция должна делать; у нас это условие задачи. Три вида проверок:

1. **Обычные** — по примеру из каждой группы: ребёнок, школьник, взрослый.
2. **Граничные.** <Term id="edge-case">Граничные случаи</Term> — значения на стыке групп и по обе стороны от него (6 и 7, 17 и 18), ноль, пустой список, один элемент, повторяющиеся значения (две одинаковые оценки).
3. **«Плохие»** — неверные данные: отрицательный возраст. Функция должна выбросить исключение, как обещает её описание, а не вернуть что попало.

</Theorem>

Полный набор проверок для билета:

```python
def ticket_price(age):
    """Цена билета: до 7 лет — 0, 7–17 — 250, с 18 — 500; age < 0 — ValueError."""
    if age < 0:
        raise ValueError(f"возраст не может быть отрицательным: {age}")
    if age < 7:
        return 0
    if age < 18:
        return 250
    return 500

# обычные
assert ticket_price(4) == 0
assert ticket_price(12) == 250
assert ticket_price(40) == 500
# граничные
assert ticket_price(0) == 0
assert ticket_price(6) == 0
assert ticket_price(7) == 250
assert ticket_price(17) == 250
assert ticket_price(18) == 500
```

## Проверить, что исключение выброшено

С «плохим» входом `assert ticket_price(-1) == ...` не написать: функция ничего не вернёт, она выбросит `ValueError`. Помогут флаг и обработка исключений:

```python
raised = False
try:
    ticket_price(-1)
except ValueError:
    raised = True
assert raised, "ticket_price(-1) должна выбросить ValueError"
print("все проверки прошли")
```

```
все проверки прошли
```

Выбросит функция `ValueError` — флаг станет `True`; вернёт число — `assert` упадёт; выбросит другое исключение — его никто не поймает, тоже провал. В разделе «Тестирование» дисциплины «Объектно-ориентированное программирование» для этого есть запись в одну строку, а устроена она так же.

## Проверки ищут ошибки, а не доказывают их отсутствие

Нидерландский учёный Эдсгер Дейкстра в работе «Notes on Structured Programming» (1970) писал, по сути, так: тестирование может показать, что ошибки есть, но не может доказать, что их нет. Все проверки прошли — значит, на *этих* входах функция отвечает так, как ожидают проверки. Про остальные входы они молчат.

Поэтому набор проверок оценивают так: поймает ли он *сломанную* версию функции:

<div className="table-scroll">

| Сломанная версия | Обычные | Граничные | «Плохой» вход |
|---|---|---|---|
| `age <= 7` вместо `age < 7` | проходят | `ticket_price(7)` падает | проходит |
| `age < 17` вместо `age < 18` | проходят | `ticket_price(17)` падает | проходит |
| перепутаны цены 250 и 500 | падают | падают | проходит |
| нет `if age < 0` | проходят | проходят | падает |

</div>

Каждый вид проверок ловит свои ошибки. Перепутанные цены поймали и граничные проверки, но обычные всё равно пишут: с них начинают, они понятны читателю и страхуют, если границы в условии потом сдвинутся.

## Проверки — по условию, а не по коду

Условие: «Средняя оценка по журналу. Оценки в журнале — тексты `"5"`, `"4"`, …; `"н"` означает пропуск и не учитывается. Если оценок нет — вернуть 0. Округлить до двух знаков». Ассистент предложил:

```python
def average_mark(marks):
    return round(sum(int(m) for m in marks if m != "н") / len(marks), 2)
```

Выглядит уверенно, на `["5", "4", "3"]` даёт `4.0` — верно. Не читая код, напишем проверки по условию:

```python
assert average_mark(["5", "4", "3"]) == 4                       # обычный
assert average_mark(["н"]) == 0                                 # граничный: оценок нет
assert average_mark(["5", "н", "3"]) == 4, f"получили {average_mark(['5', 'н', '3'])}"
```

## Правила работы с кодом ассистента

- **Проверки пишите сами и по условию.** Тесты ассистента к своему же коду часто повторяют его ошибку.
- **Не переписывайте ожидание из вывода.** «Получил 2.67, вписал `== 2.67`» — так проверка закрепляет ошибку. Ответ считайте сами, по условию.

## Ловушка: скобки вокруг assert

```python
x = 5
assert (x > 10, "x должен быть больше 10")
print("прошло")
```

```
C:\work\check.py:2: SyntaxWarning: assertion is always true, perhaps remove parentheses?
  assert (x > 10, "x должен быть больше 10")
прошло
```

В скобках — кортеж из двух элементов, а непустой кортеж всегда истинен. Такой `assert` не проверяет ничего. На компьютере Python предупреждает об этом (`SyntaxWarning` — предупреждение, а не ошибка), но в песочнице курса предупреждения не видно — тем важнее знать ловушку. Пишите без скобок: `assert x > 10, "x должен быть больше 10"`.

## Ловушка: assert для проверки данных

`assert` — проверка *своего кода*: «если тут ложь, у меня баг». С ключом запуска `-O` (`python -O program.py`) Python пропускает все `assert`. Поэтому всё, что приходит снаружи, — от пользователя, из файла, от чужого кода, — проверяют через `if` и `raise ValueError(...)`, как в функции `parse_age`.

## Изнанка: как платформа проверяет задачи

Задачи с функциями платформа проверяет так же, как вы: сначала запускает ваш код, чтобы функции были определены, а потом по очереди выполняет свои проверки, например:

```python
assert square(3) == 9, "square(3) должно вернуть 9"
```

Проверка прошла — тест засчитан. Упала с `AssertionError` — тест провален, и вы видите текст после запятой. Упала с другим исключением — вы видите его тип и текст. Каждую проверку платформа выполняет отдельно, поэтому одна упавшая не мешает остальным.

Те же проверки с инструментом `pytest` вы будете писать в разделе «Тестирование» дисциплины «Объектно-ориентированное программирование».
